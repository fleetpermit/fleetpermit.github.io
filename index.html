    FleetPermit in five answers

    1. What is FleetPermit?

      Least privilege for agents, across every cluster.

      Define who can call which MCP tool, on which clusters, and for how long.

      EvidenceHow the architecture works

    2. What is new?

      Fleet-wide, time-bound authorization for agent-to-tool calls.

      Open Cluster Management places one policy across a fleet, and short-lived leases activate it. The expiry is enforced inside the gateway rule itself, so it holds even when the hub is unreachable. FleetPermit does not serve tools; it governs calls to the MCP servers you already run.

      EvidenceWhy no managed-cluster agent is needed

    3. What works today?

      1. OCM Placement
      2. FleetPermit policy and lease
      3. Kubernetes Agentic Networking XAccessPolicy on Envoy
      4. MCP ALLOW or DENY

      The whole path runs on real clusters: 1 hub and 3 managed clusters.

      Why FleetPermit

      Agents that operate clusters need some authority. FleetPermit limits how much, for how long, and on which clusters.

      Standing access is the default

      Agent integrations tend to hold access for as long as they are installed. FleetPermit makes access time-bound: a ToolAccessLease activates specific tools for a set duration, and the gateway stops honouring it at the expiry time.

      A fleet is not one cluster

      The same rule has to hold on every cluster, including ones that are temporarily unreachable. FleetPermit uses an Open Cluster Management Placement to decide where a grant may exist and ManifestWork to deliver it. Clusters outside the placement never receive one.

      Tools are the unit of risk

      get_cluster_health and read_secret on the same server deserve different answers. Policies name MCP tools, and the gateway checks the tool name and the caller's SPIFFE identity on every call.

      Errors never add authority

      With the default-deny anchor installed, a missing Placement, a render error or a deleted policy withdraws grants, and nothing else changes. With the hub unreachable, nothing new is granted and delivered leases still expire on time. failMode accepts only Closed. The anchor matters because upstream enforces nothing on a backend without any XAccessPolicy; on clusters FleetPermit selects, its inert policy also denies.

      How it works

      One Go controller on the hub. No FleetPermit component runs on managed clusters.

      1. Define the ceiling

        The platform team writes a FleetAccessPolicy: which SPIFFE identities, which OCM Placement, which tool server, which MCP tools, and the longest lease allowed.

      2. Request a lease

        Someone creates a ToolAccessLease for a subset of those tools, for example restart_workload for 10 minutes during incident 42. The lease can narrow the clusters, never widen them. Its spec is immutable.

      3. Check WHO, WHAT, HOW LONG and WHERE

        The controller confirms the subject is in the policy, the tools are a subset of its permissions, the duration is within maxDuration, and reads the clusters from the OCM PlacementDecision. A failed subject, tool or duration check marks the lease Denied, which is terminal. A lease whose clusters are not placed waits in Pending.

      4. Render and deliver

        For each selected cluster it renders one XAccessPolicy with one CEL rule per lease, such as request.mcp.tool_name in ['restart_workload'] && request.time < timestamp('2026-09-26T10:15:00Z'), stamps a SHA-256 content digest, and delivers it with one ManifestWork. Status feedback marks the lease Ready.

      5. Enforce and expire

        The kube-agentic-networking controller programs the Envoy gateway. Envoy checks identity, tool and time on every tools/call, so at expiry it denies by itself, even if the hub is unreachable. MCP session methods such as initialize, tools/list and ping have no time bound in the gateway; the controller removes that session rule after the subject's last grant ends. The controller then withdraws the grant. If no other grant remains on that cluster, an inert policy that allows nothing stays in place.

      A 30-second example

      A policy that is the ceiling, and a lease that activates part of it for ten minutes.

      fleetaccesspolicy.yaml
      apiVersion: fleetpermit.github.io/v1alpha1
kind: FleetAccessPolicy
metadata:
  name: sre-remediation
  namespace: fleet
spec:
  subjects:
    - spiffeID: spiffe://cluster.local/ns/agents/sa/sre-agent
  placement:
    provider: ocm
    placementRef:
      name: production-clusters   # selects env=production
  target:
    protocol: MCP
    namespace: mcp-tools
    ref:
      kind: XBackend
      name: fleet-tools
  permissions:
    - tool: get_cluster_health
    - tool: restart_workload
    - tool: scale_workload
  lease:
    required: true
    defaultDuration: 15m
    maxDuration: 30m
  enforcement:
    provider: kubernetes-agentic-networking
    failMode: Closed
      toolaccesslease.yaml
      apiVersion: fleetpermit.github.io/v1alpha1
kind: ToolAccessLease
metadata:
  name: incident-42
  namespace: fleet
spec:
  policyRef:
    name: sre-remediation
  subject:
    spiffeID: spiffe://cluster.local/ns/agents/sa/sre-agent
  permissions:
    - tool: restart_workload
  duration: 10m
  reason: "INC-42: checkout pods crash-looping"

      Security properties

      What holds, and the mechanism that makes it hold.

      Security properties and how FleetPermit enforces them
      PropertyMechanism
      Time bound in the data planeEvery lease rule carries request.time < timestamp(expiresAt), evaluated by Envoy on each call. Expiry does not depend on the hub.
      Default deny with the anchorThe shipped default-deny anchor, an XAccessPolicy installed next to each tool backend, makes a backend with no grant refuse every call. Upstream enforces nothing on a backend without any XAccessPolicy, so the anchor is part of the installation.
      Identity from the platformAgents present SPIFFE X.509 certificates issued by Kubernetes Pod Certificates; the gateway authenticates them over mTLS.
      Only narrowing, never wideningA lease activates a subset of the policy's tools, for at most maxDuration, on at most the placement's clusters.
      Narrow controller RBACOn the hub, the controller reads placement and writes ManifestWork. It cannot read Secrets or create pods, RBAC or namespaces. The OCM work agent applies whatever a ManifestWork carries, so the controller's ServiceAccount is still a privileged credential; --work-executor makes the work agent apply FleetPermit's content as a restricted managed-cluster identity.
      Errors never add authorityWith the default-deny anchor installed, render errors or a missing Placement withdraw grants, and lease grants expire on time. Denied and Expired leases are terminal. failMode accepts only Closed.
      Traceable contentEach rendered object carries a SHA-256 content digest and source annotations. Drifted objects are restored from the hub.

      Built on open projects

      FleetPermit adds one controller and two APIs. Everything else is existing open source.

      • KubernetesCustom resources, admission validation, Pod CertificatesCNCF Graduated

      • Gateway APIThe gateway that fronts each tool serverKubernetes SIG Network
      • EnvoyEvaluates identity, tool and time on every callCNCF Graduated
      • SPIFFEWorkload identities for agentsCNCF Graduated

      Get started

      The lab creates one hub and three managed kind clusters on your machine, installs everything, and runs the narrated demo.

      local lab
      $ git clone https://github.com/fleetpermit/fleetpermit
$ cd fleetpermit
$ make demo-up     # 1 hub + 3 managed kind clusters
$ make demo-run    # narrated authorization demo
$ make test-e2e    # real multi-cluster scenarios
$ make demo-down
      existing fleet
      # on the OCM hub
$ helm install fleetpermit charts/fleetpermit -n fleetpermit-system --create-namespace
# on each managed cluster
$ kubectl apply -f config/managed-cluster/work-agent-rbac.yaml
$ kubectl apply -f config/managed-cluster/default-deny-anchor.yaml
