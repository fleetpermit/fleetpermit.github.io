Architecture

One controller on an Open Cluster Management hub decides. The gateway on each managed cluster enforces identity, tool and time on every call.

How it works

  1. Define the ceiling

    The platform team creates a FleetAccessPolicy and an OCM Placement. The policy lists SPIFFE subjects, the Placement, the target (namespace plus XBackend or Gateway), the permitted MCP tools and the lease limits. failMode is Closed.

  2. Request a lease

    Someone creates a ToolAccessLease, for example incident-42: restart_workload for 10 minutes, with a reason. The spec is immutable.

  3. Check

    The controller checks WHO (the subject is in the policy), WHAT (the tools are a subset of its permissions), HOW LONG (the duration is at most maxDuration) and WHERE (the OCM PlacementDecision, which a lease may only narrow).

  4. Render and deliver

    It renders one XAccessPolicy per policy and cluster with one CEL rule per lease, plus an MCP session rule for initialize and tools/list, stamped with SHA-256 content digest annotations. One ManifestWork per cluster delivers it.

  5. Apply and report

    The OCM work agent applies it, the agentic networking controller programs Envoy, and acceptance flows back through ManifestWork status feedback. The lease becomes Ready once every cluster reports the current digest.

  6. Call

    The agent calls the tool through the gateway with its mTLS SPIFFE identity. Envoy checks identity, tool and time and allows it. An unselected cluster, a wrong identity or an unlisted tool is denied.

  7. Expire

    At expiry Envoy itself denies, because the time bound is part of the rule. This holds even when the hub is unreachable. The controller then replaces the grant with an inert policy that allows nothing, so the cluster stays wired for the next lease.

Lease lifecycle

expiresAt is the API server's creation time plus the lease duration. It is computed once from immutable inputs and never extended. To change a lease, delete it and create a new one, so every grant is traceable to exactly one request.

Why no managed-cluster agent is needed

A lease has to stop working on time even if the hub, OCM or FleetPermit is unavailable. The upstream XAccessPolicy API has no expiry field, but its reference implementation accepts CEL authorization rules and allows request.time as a variable. Each lease therefore becomes one rule that contains its own expiry:

CEL rule evaluated by Envoy on every tools/call
request.mcp.tool_name in ['restart_workload'] && request.time < timestamp('2026-09-26T10:15:00Z')

Envoy compiles it into an RBAC condition and stops honouring the grant at the expiry instant using the managed cluster's clock. Nothing on the hub needs to be reachable. The controller removes expired grants afterwards; that is cleanup, not enforcement.

What gets rendered

For policy sre-remediation with lease incident-42 on cluster-east. Identifiers are shortened.

XAccessPolicy delivered by ManifestWork
apiVersion: agentic.networking.x-k8s.io/v1alpha1
kind: XAccessPolicy
metadata:
  name: fleetpermit-sre-remediation-a46c9779
  namespace: mcp-tools
  labels:
    app.kubernetes.io/managed-by: fleetpermit
  annotations:
    fleetpermit.github.io/policy: fleet/sre-remediation
    fleetpermit.github.io/cluster: cluster-east
    fleetpermit.github.io/expires-at: "2026-09-26T10:15:00Z"
    fleetpermit.github.io/content-digest: sha256:8a5e41c4...
spec:
  targetRefs:
    - {group: agentic.networking.x-k8s.io, kind: XBackend, name: fleet-tools}
  action: Allow
  rules:
    - name: session-3f2a9c1b0d   # MCP session methods for this subject
      source: {type: SPIFFE, spiffe: spiffe://cluster.local/ns/agents/sa/sre-agent}
      authorization:
        type: Inline
        mcp: {mcpBaseProtocolMethodsOption: MATCH_BASE_PROTOCOL_METHODS}
    - name: lease-7c41d2e9aa     # the lease: tools/call, bounded in time
      source: {type: SPIFFE, spiffe: spiffe://cluster.local/ns/agents/sa/sre-agent}
      authorization:
        type: CEL
        cel:
          expression: "request.mcp.tool_name in ['restart_workload'] && request.time < timestamp('2026-09-26T10:15:00Z')"

The content digest is SHA-256 over the canonical JSON of the policy UID, the cluster, the object's name and namespace, and its spec. Identical inputs give identical digests; any change to tools, subject, expiry or target changes it.

Limits

  • Experimental upstream APIsXAccessPolicy (v1alpha1) and XBackend (v0alpha0) are experimental and may change.
  • No argument-level matchingkube-agentic-networking v0.2.0 matches the tool name only, so a limit such as replicas=1000 cannot be enforced (S16).
  • CapacityUpstream allows at most 5 XAccessPolicies per target and 10 rules per policy, which leaves room for about 9 concurrent lease grants per policy per cluster. Excess leases are reported CapacityExceeded.
  • Session methodsMCP session methods (initialize, tools/list) are not time-bounded in the data plane. The controller removes them after the subject's last grant ends.
  • ClocksExpiry uses each managed cluster's clock, so clock skew shifts the moment of denial.
  • Lab, not benchmarkThe measured results come from local kind clusters on one host, not a production benchmark.
