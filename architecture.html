Architecture

One controller on an Open Cluster Management hub decides. The gateway on each managed cluster enforces identity, tool and time on every call.

On each managed cluster

Managed cluster components
ComponentRole
OCM klusterletRegistration and work agents. Applies ManifestWork content, re-applies it on drift and reports status feedback.

How it works

  1. Define the ceiling

    The platform team creates a FleetAccessPolicy and an OCM Placement. The policy lists SPIFFE subjects, the Placement, the target (namespace plus XBackend or Gateway), the permitted MCP tools and the lease limits. failMode is Closed.

  2. Request a lease

    Someone creates a ToolAccessLease, for example incident-42: restart_workload for 10 minutes, with a reason. The spec is immutable.

  3. Check

    The controller checks WHO (the subject is in the policy), WHAT (the tools are a subset of its permissions), HOW LONG (the duration is at most maxDuration) and WHERE (the OCM PlacementDecision, which a lease may only narrow).

  4. Render and deliver

    It renders one XAccessPolicy per policy and cluster, with one CEL rule per lease and one session rule per subject for the MCP base protocol methods (initialize, tools/list, ping and others), stamped with SHA-256 content digest annotations. One ManifestWork per cluster delivers it.

  5. Apply and report

    The OCM work agent applies it, the agentic networking controller programs Envoy, and acceptance flows back through ManifestWork status feedback. The lease becomes Ready once every cluster reports the current digest.

  6. Call

    The agent calls the tool through the gateway with its mTLS SPIFFE identity. Envoy checks identity, tool and time and allows it. An unselected cluster, a wrong identity or an unlisted tool is denied.

  7. Expire

    At expiry Envoy itself denies, because the time bound is part of the rule. This holds even when the hub is unreachable. The controller then removes the grant. If no other grant remains on that cluster, an inert policy that allows nothing stays in place, so the cluster stays wired for the next lease.

Activation

A new lease becomes a working grant on the selected clusters and nowhere else.

  1. The test creates a lease for sre-agent: restart_workload and get_cluster_health for 5 minutes.
  2. FleetPermit on the hub checks it against the policy. The subject is listed, both tools are permitted, and 5 minutes is within the 10 minute maximum.
  3. The Placement selects cluster-east and cluster-west. FleetPermit renders an XAccessPolicy for each, sends it in a ManifestWork and marks the lease Active.
  4. sre-agent calls restart_workload on both clusters and gets ALLOW. The test times each cluster from lease creation to the first ALLOW.
  5. The lease reports Ready once OCM confirms the policy is applied on both clusters.
  6. cluster-edge is not selected. The same call there gets DENY, and no grant was rendered on it (S6).

Wrong tool or wrong identity

Six ways to ask for more than the policy or the lease allows. Each one is refused.

  1. Before any lease exists, sre-agent calls restart_workload on cluster-east. DENY: the policy alone grants nothing (S4).
  2. With a lease for restart_workload and get_cluster_health active, sre-agent calls read_secret. DENY: the policy does not permit that tool (S2).
  3. It calls scale_workload. DENY: the policy permits it, but the lease did not ask for it (S2).
  4. security-agent calls restart_workload. DENY: no policy lists its identity (S3).
  5. A new lease asks for restart_workload and read_secret. The hub marks it Denied with reason PermissionNotAllowed, and read_secret stays DENY (S8).
  6. A lease that asks for 1 hour, against the policy's 10 minute maximum, is Denied with reason DurationExceedsMaximum (S9).

Revocation

Deleting a lease takes the grant away on every cluster.

  1. The lease from the activation flow is still active, with a grant for sre-agent on cluster-east and cluster-west.
  2. The test deletes the lease on the hub.
  3. FleetPermit renders the policy for both clusters again, without the lease's rule, and updates their ManifestWorks.
  4. sre-agent calls restart_workload on both clusters until each answers DENY. The test times each cluster from the delete to the first DENY.

Expiry

The gateway stops honouring a lease at its expiry time.

  1. The test creates two leases for sre-agent: get_cluster_health for 40 seconds and restart_workload for 100 seconds.
  2. Each lease becomes its own rule, with its expiry time written into it. Both tools get ALLOW on cluster-west.
  3. The test waits until just before the shorter lease expires, then keeps calling get_cluster_health.
  4. Once request.time passes the expiry, the rule no longer matches and Envoy answers DENY. The test times the gap from expiresAt to the first DENY.
  5. restart_workload still gets ALLOW, because its own lease has not expired (S13).
  6. The controller then marks the lease Expired and removes its rule. S5 does not check this step. The hub-disconnected flow shows it for another lease.

Hub disconnected

The whole hub is paused before a lease expires. The clusters still deny on time.

  1. The test creates a 50 second lease for restart_workload. cluster-east and cluster-west both answer ALLOW.
  2. It pauses the hub node. The hub API, FleetPermit and the hub's etcd all stop. A call to cluster-east still gets ALLOW.
  3. At the expiry time both gateways answer DENY. The rendered policy is still on cluster-east, so the DENY comes from the time bound in the rule (S11).
  4. The test resumes the hub. FleetPermit marks the lease Expired and withdraws the stale grants from both clusters.
  5. Calls stay DENY. The test times the clean-up from the moment the hub resumed (S12).

Placement change

When cluster labels change, the grant follows the Placement.

  1. The test creates a 10 minute lease for restart_workload. cluster-west answers ALLOW and cluster-edge answers DENY.
  2. It changes the labels on the hub: cluster-west becomes env=staging and cluster-edge becomes env=production.
  3. The Placement now selects cluster-east and cluster-edge. FleetPermit delivers the grant to cluster-edge and withdraws it from cluster-west.
  4. cluster-west now answers DENY and cluster-edge answers ALLOW. The test times both from the label change.
  5. The test then restores the original labels.

Drift repair

Someone deletes the delivered policy on a cluster. The backend stays closed until the hub puts it back.

  1. cluster-west holds a rendered XAccessPolicy with an active grant for restart_workload.
  2. The test deletes that XAccessPolicy directly on cluster-west, without going through the hub.
  3. Two seconds later the test expects DENY, unless the policy is already back. While only the default-deny anchor is left, the backend stays closed.
  4. At its next status sync, OCM reports the object missing. FleetPermit then asks the work agent to re-apply it at once.
  5. The policy is back and the call gets ALLOW again. The test times this from the delete.

Default-deny anchor

Why every backend carries a policy whose only rule never matches.

  1. cluster-edge is not selected, so FleetPermit sends it nothing. The only XAccessPolicy on its backend is the default-deny anchor, whose rule never matches.
  2. The test deletes the anchor. Now no XAccessPolicy targets the backend.
  3. sre-agent calls read_secret on cluster-edge. Upstream enforces nothing on a backend without a policy, and the lab observed ALLOW. The test records this call but does not require it.
  4. The test puts the anchor back. The same call gets DENY.

Controller restarts

Restarting the controllers does not interrupt an active grant.

  1. An active lease lets sre-agent call restart_workload on cluster-east.
  2. The test deletes the FleetPermit controller pod on the hub and makes 20 calls while it comes back.
  3. It then restarts the agentic-networking controller on cluster-east and makes 20 more calls.
  4. Every call must get ALLOW. Envoy keeps enforcing the rules it already has while the controllers restart.
  5. Afterwards a new lease for get_cluster_health gets ALLOW on cluster-east.

Lease lifecycle

expiresAt is the API server's creation time plus the effective duration. For a lease without spec.duration, that is the policy default in effect at the first evaluation, pinned in status; policy changes never extend it. Only the controller should be allowed to write lease status. To change a lease, delete it and create a new one, so every grant is traceable to exactly one request.

Why no managed-cluster agent is needed

A lease has to stop working on time even if the hub, OCM or FleetPermit is unavailable. The upstream XAccessPolicy API has no expiry field, but its reference implementation accepts CEL authorization rules and allows request.time as a variable. Each lease therefore becomes one rule that contains its own expiry:

CEL rule evaluated by Envoy on every tools/call
request.mcp.tool_name in ['restart_workload'] && request.time < timestamp('2026-09-26T10:15:00Z')

Envoy compiles it into an RBAC condition and stops honouring the grant at the expiry instant, using the managed cluster's clock. Nothing on the hub needs to be reachable. The controller removes expired grants afterwards as cleanup; enforcement has already happened in the gateway.

What gets rendered

For policy sre-remediation in namespace fleet, with lease incident-42, on cluster-east. UIDs and the digest are shortened.

XAccessPolicy delivered by ManifestWork
apiVersion: agentic.networking.x-k8s.io/v1alpha1
kind: XAccessPolicy
metadata:
  name: fleetpermit-sre-remediation-a46c9779b9dca599
  namespace: mcp-tools
  labels:
    app.kubernetes.io/managed-by: fleetpermit
    fleetpermit.github.io/policy-uid: 3b9f6a2e-...
  annotations:
    fleetpermit.github.io/policy: fleet/sre-remediation
    fleetpermit.github.io/policy-uid: 3b9f6a2e-...
    fleetpermit.github.io/policy-generation: "1"
    fleetpermit.github.io/cluster: cluster-east
    fleetpermit.github.io/lease-uids: 7c41d2e9-...
    fleetpermit.github.io/expires-at: "2026-09-26T10:15:00Z"
    fleetpermit.github.io/content-digest: sha256:8a5e41c4...
spec:
  targetRefs:
    - {group: agentic.networking.x-k8s.io, kind: XBackend, name: fleet-tools}
  action: Allow
  rules:
    - name: session-c8735226c1   # MCP base protocol methods for this subject
      source: {type: SPIFFE, spiffe: spiffe://cluster.local/ns/agents/sa/sre-agent}
      authorization:
        type: Inline
        mcp: {mcpBaseProtocolMethodsOption: MATCH_BASE_PROTOCOL_METHODS}
    - name: lease-7c41d2e9aa     # the lease: tools/call, bounded in time
      source: {type: SPIFFE, spiffe: spiffe://cluster.local/ns/agents/sa/sre-agent}
      authorization:
        type: CEL
        cel:
          expression: "request.mcp.tool_name in ['restart_workload'] && request.time < timestamp('2026-09-26T10:15:00Z')"

The object name ends in the first 16 hex characters of the SHA-256 of the policy's namespace/name; the ManifestWork on the hub has the same name. The session rule allows the MCP base protocol methods for its subject: initialize, tools/list, ping, methods under completion/, logging/ and notifications/, the event stream and session close. Only lease rules allow tools/call.

The content digest is SHA-256 over the canonical JSON of the policy UID, the cluster, the object's name and namespace, and its spec. Identical inputs give identical digests, and any change to tools, subject, expiry or target changes it.

Limits

  • Experimental upstream APIsXAccessPolicy (v1alpha1) and XBackend (v0alpha0) are experimental and may change.
  • No argument-level matchingkube-agentic-networking v0.2.0 matches the tool name only, so a limit such as replicas=1000 cannot be enforced (S16).
  • CapacityUpstream allows at most 5 XAccessPolicies per target and 10 rules per policy, which leaves room for about 9 concurrent lease grants per policy per cluster. Excess leases are reported CapacityExceeded; a lease that fits on no cluster waits in Pending until capacity frees up.
  • Session methodsThe MCP base protocol methods (initialize, tools/list, ping and others) are allowed by a per-subject rule with no time bound in the data plane. They cannot call tools, and the controller removes the rule after the subject's last grant ends.
  • How upstream combines policieskube-agentic-networking v0.2.0 combines the Allow policies on a target with OR, while its API documentation says all of them must allow a request. The default-deny anchor depends on the implemented behaviour.
  • ClocksExpiry uses each managed cluster's clock, so clock skew shifts the moment of denial.
  • Local labThe measured results come from local kind clusters on one host. They are not a production benchmark.
